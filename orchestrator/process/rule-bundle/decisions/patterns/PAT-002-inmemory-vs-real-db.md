# PAT-002 — 内存/嵌入库 vs 真 DB

> 持久化底座选型。判据沿用 `PAT-001` 的 BG/BF 双闸形态。

## 1. 触发条件(TRIG)
- **TRIG-002**:要为某数据选存储底座——原型期常想用内存/嵌入库(in-memory pglite、SQLite 文件、Map)图快;此卡判定该不该。

## 2. 推荐默认
默认**真 DB(Postgres 等服务型)**,除非命中下面 LIGHT-GATE 全过(纯一次性脚本 / 确定性测试夹具)。

## 3. 判据
### LIGHT-GATE(全过才允许用内存/嵌入档)
- **LG-001** 无跨实体事务、无唯一约束 / 外键完整性需求
- **LG-002** 数据**无需重启存活**(纯测试夹具 / 一次性演示 / 派生缓存)
- **LG-003** 单进程、无并发写
- **LG-004** 被仓库接口隔离,将来换真 DB 不动业务(可逆)

### REAL-FORCE(任一命中即强制真 DB)
- **RF-001** 契约含跨实体事务 / 唯一约束 / 外键完整性
- **RF-002** 存在**用户产生且需留存**的数据(重启/刷新不能丢)
- **RF-003** 多连接 / 并发 / 将来要部署多实例
- **RF-004** 需要正规迁移演进 schema(而非每次重建)

## 4. 可观测证据 + 保守默认
| 判据 | 查什么 | 缺证据时 |
|---|---|---|
| RF-001 | 翻契约/schema 有无 `unique` / `foreignKey` / 事务 | 不明 → 倾向真 DB |
| RF-002 | 有没有"用户操作产生、期望下次还在"的数据 | 不明 → 倾向真 DB |

## 5. 过往应用(链 LESSON_LEDGER)
| 日期 | 对象 | 落档 | 触发判据 | 结局(T+N) | Ref |
|---|---|---|---|---|---|

> 反例教训(LED 关联):原型期用内存 pglite 当持久化用,"切页/重启就丢",被用户直接判定为「假的」——RF-002 当时被忽略。

## 6. 反模式速查
- ❌ 内存/嵌入库当"真持久化"用(RF-002 没认)。
- ❌ 测试用一种引擎、运行用另一种**且不验证**——本仓刻意让测试 pglite 跑同一套 drizzle-kit 迁移来化解漂移(见 P1 测试策略)。
- ❌ 没有正规迁移、靠 `CREATE TABLE IF NOT EXISTS` 启动建表,改 schema 只能重建库(RF-004)。
- ❌ 持久库下沿用进程级**确定性 id 计数器** → 跨重启 PK 碰撞(CreatorOS 注册/登录 500;修为进程唯一 id)。
- ❌ 只用 canonical 种子数据 + 特权账号测,从不以**冷启动新用户**验隔离 → 漏多租户泄漏(看似有数据其实是别人的)。
