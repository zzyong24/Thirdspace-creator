## 权威边界与维护规则

1. `PRODUCT_SPEC.md` 决定产品是什么、做什么、有哪些 ID；本文件决定这些内容在 UI、Agent 回复、
   通知、引导、空状态、确认、拒绝、进度、错误和成功反馈中怎么说。
2. 面向用户的名词、动作和状态必须优先来自用户真实工作的产品领域。个人品牌、内容发行、CRM、
   客户跟进、商机、内容矩阵、学习目标、健康指标、现金流、复盘、预算、关系承诺、重要时刻等词，
   目标用户本来就会，直接使用，不要为了“通俗”把它们改成含糊的“东西”“数据”“操作”。
3. 软件实现词及其生硬直译不得进入普通用户界面。把 `Entity` 写成“实体”、把 `canonical state`
   写成“规范状态”、把 `CRUD` 写成“增删改查”，仍然算违规。
4. 一个词即使出现在 SPEC、代码、接口或测试里，也不自动获得用户面使用权；自动扫描未报错也不代表
   文案合格。诊断细节只能放在次级支持信息中，普通用户只看到“参考编号”。
5. 新增用户可见概念时，先补“产品领域词库”或“实现术语翻译表”，再写 PAGE_SPEC、UI 文案和 Agent
   提示词。产品负责人确认用户叫法，agent 维护引用、示例与同步状态。
6. SPEC 改了产品含义、范围或状态机：先改 SPEC，再同步本文件。只改叫法或句式：只改本文件，不反向
   改写 SPEC。两者冲突时，SPEC 裁决“是什么意思”，本文件裁决“用户看到什么词”。
7. 稳定 ID、代码名、字段名和协议名保持原文，作为元数据、实现与追溯依据；除“参考编号”外，不渲染
   到普通用户可见文案。

## 边界词判断

遇到模糊词，先问：**目标用户在不讨论软件实现时，会不会用这个词完成真实工作？**

- 会：把它当产品领域词使用，例如 CRM 的“商机”、财务的“现金流”、日历里的“事件”。
- 不会：隐藏或翻译成用户正在做的动作、对象和结果。
- 同一个词两种含义都有：按句中职责判断。例如“服务”指客户购买的服务时保留；指后端 service 时，
  改成具体功能或完全不显示。
- 仍不确定：先用“具体对象 + 具体动作 + 用户结果”改写，并把决定登记在下表；不要把判断推给用户。

## 实现术语翻译表（按用户任务意图分簇）

以下是默认起点，不是逐字替换字典。填写“本项目最终说法”时，应落到上面的产品领域词；如果普通用户
根本不需要知道这个概念，写“隐藏”，不要硬造一个温和版本的工程词。

| 簇 | 软件 / 形式化词（用户面禁用） | 默认改写方向 | 本项目最终说法 | 允许保留的边界 |
| --- | --- | --- | --- | --- |
| 接入与来源 | `Connector` | 数据来源、已连接账号、导入渠道 | `<填写>` | 仅软件开发者产品可保留并注明角色 |
| 接入与来源 | `Manifest` | 已安装内容、功能清单；不影响任务时隐藏 | `<填写或“隐藏”>` | 仅用户确实在编辑清单文件时 |
| 接入与来源 | `service` | 具体功能、处理方；直接说用户获得的服务 | `<填写>` | “客户购买的服务”等业务含义可保留 |
| 工作推进 | `pipeline` | 当前流程、处理步骤、发行进度 | `<填写>` | 销售人员本来就说“销售管道”时可登记保留 |
| 工作推进 | `event` | 具体发生的事：发布、付款、跟进、打卡 | `<填写>` | 日历事件、营销事件等业务含义可保留 |
| 业务对象 | `Domain` | 直接说个人品牌、CRM、学习、健康、财务等业务区 | `<填写>` | 软件架构语境只留内部 |
| 业务对象 | `Entity` | 直接说客户、内容、商机、预算、承诺等对象 | `<填写>` | 软件开发者产品可登记例外 |
| 业务对象 | `bounded context` | 各业务区的职责范围；用户无需知道时隐藏 | `<填写或“隐藏”>` | 架构诊断页可作为次级信息 |
| 业务对象 | `aggregate` | 汇总、概览，或具体集合名 | `<填写>` | 统计分析中的业务“汇总”可用 |
| 信息与版本 | `Snapshot` | 某时点记录、已保存版本、当时情况 | `<填写>` | 用户确实比较历史版本时可用“快照” |

| 信息与版本 | `schema` | 所需信息、内容格式；不需要解释时隐藏 | `<填写或“隐藏”>` | 数据建模工具的专业用户可登记例外 |
| 生效与替换 | `canonical` / `canonical state` | 当前采用、当前有效、现在以此为准 | `<填写>` | 只留在 SPEC、代码和诊断中 |

## UI 状态文案句式

先替换花括号，再按产品语气微调；每句话都使用本文件中的权威词。

| 状态 | 固定结构 | 句式模板 |
| --- | --- | --- |
| 空状态 | 当前事实 → 价值或原因 → 一个下一步 | `还没有{产品对象}。{为什么需要它或创建后能得到什么}。[{明确动作}]` |
| 确认 | 动作 → 用户影响 → 可恢复性 → 明确按钮 | `要{具体动作}吗？这会{用户可理解的影响}。{能否撤销或如何恢复}。[{确认动作}] [取消]` |
| 拒绝 | 未执行 → 领域原因 → 可行下一步 | `现在不能{具体动作}，因为{用户能理解的领域原因}。你可以先{下一步}。` |
| 进行中 | 正在做什么 → 是否需要等待 / 避免重复 | `正在{具体动作}…{可以离开此页，完成后会通知你 / 请不要重复提交}` |
| 出错 | 什么没完成 → 影响 → 下一步 → 次级编号 | `{对象或动作}没有完成。{钱、数据或工作是否受影响}。请{重试或恢复动作}。参考编号：{编号}` |
| 已保存 | 已完成结果 → 当前生效状态 / 下一步 | `{产品对象}已保存。{现在以哪个版本为准，或用户接下来可以做什么}。` |

## 交付前检查

- [ ] 角色、核心对象、动作、状态和结果已经填成当前产品的领域词，不是通用占位词。
- [ ] PAGE_SPEC、UI_RULES、Agent 提示词、通知和所有状态文案都以本文件为词汇权威。
- [ ] 用户面没有软件实现词、生硬直译、控制 ID、字段名或机器错误码。
- [ ] 产品领域专业词被保留，没有为了“通俗”损失业务精度。
- [ ] 每个空状态、拒绝和错误都给出一个真实可执行的下一步。
- [ ] SPEC 变更后已检查本文件；只改文案时没有误改 SPEC 的产品含义或稳定 ID。
- [ ] 自动可见文案扫描已通过，并完成一次人工语境检查；扫描通过只是底线，不是文案结论。
