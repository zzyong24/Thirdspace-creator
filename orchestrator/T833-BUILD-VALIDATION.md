# T-833 构建与验证记录

日期：2026-08-14

## 用户可见结论

- “历史作品重建”的 `must NOT have additional properties` 不是用户资料损坏，也不是数据库错误。模型返回了契约外字段；旧实现把整个对象判失败，文本兜底再次返回同类对象后仍然失败。
- 同一回复中的多张局部改稿卡原先都绑定同一个旧稿版本。采纳第一张会产生新版本，第二张即使修改另一段，也会被旧版本门直接拒绝。

## 修复范围

1. effective JSON Schema 增加协议级归一化：仅当 schema 明确声明 `additionalProperties:false` 时，删除模型多返回的顶层或嵌套字段；随后继续用原 schema 严格校验。缺必填字段、类型错误、枚举错误等仍然失败，不补造内容。
2. 局部改稿应用改为读取权威当前稿。旧候选的目标段原文若仍完全一致，可安全接在当前版本后生成新版本；目标段已改变、已删除、候选为空或 no-op 时继续拒绝。
3. 应用接口返回本次写入前的权威版本。每张卡撤销时同时提交自己写出的版本 ID；若之后已有其他卡或用户产生新版本，撤销会被拒绝，避免旧卡覆盖后续修改。
4. 版本追加与当前指针移动现已放入同一个数据库事务，并用 `expectedCurrentVersionId` 条件更新；
   并发竞争只有一个写入成功，失败事务连新版本行一并回滚。撤销同样使用原子条件更新，不再
   “先检查、后无条件恢复”。`previousVersionId` 由成功写入服务直接返回，不再由 transport 提前读取。

## TDD 证据

- 红测：effective schema 遇到顶层和嵌套额外字段时，稳定复现 `must NOT have additional properties`；修复后通过。
- 红测：两张基于同一旧稿、修改不同段落的候选，第二张原先因 stale version 失败；修复后两张均可采纳，并保留第一张修改。
- 防回归：旧候选目标段已修改时仍冲突；缺必填字段仍 fail-closed；后续已有新版本时旧卡撤销仍冲突。
- 并发红测：两个候选从同一当前版本同时写入时旧实现两者都成功；修复后恰好一个成功、一个冲突，
  且版本表只新增成功的一行。陈旧条件撤销保持当前指针不变。
