# T-835 制作分镜非阻断恢复验证

日期：2026-08-14

## 根因

两阶段写稿先冻结完整连续口播，再让分镜模型返回 `shots[]`。旧实现要求模型把长口播逐字符复述进每一段；两次输出拼接后只要有一个字符、标点或空白不一致，就取消整次候选并提示用户检查模型。完整性保护是必要的，但把“原文真值”交给概率模型复述，导致第二阶段技术失败会错误阻断已经成功的第一阶段口播。

## 当前行为

1. 模型分镜逐字一致：直接使用模型分镜。
2. 仅空格、换行等空白分隔漂移：按照冻结原文重新锚定每段口播，保留模型给出的 role、画面、字幕、时长和 visual。
3. 模型真实增删改口播：最多再请求一次分镜；仍不一致时，从冻结原文确定性切出基础分镜候选。
4. 分镜模型鉴权、网络、协议或结构化输出失败：不再取消整稿，直接从冻结原文生成基础分镜候选。
5. 基础分镜只填“主播口播 + 与本段原文一致的画面”等不含新事实的通用字段；所有 `shots[].口播` 均是冻结原文的连续切片，拼接后逐字符和 SHA-256 保持一致。
6. 候选记录 `storyboardRecovery`：恢复模式、原因、首个差异位置、期望/实际长度与脱敏模型诊断；质量提醒明确告诉用户已使用基础分镜，但候选仍可采纳。
7. 目标时长短于基础镜头数时，每镜仍至少 1 秒并保持首尾连续、不重叠、不产生零时长镜头；
   无法物理容纳时诚实延长基础分镜总时长，而不是伪造重叠时间轴。

## TDD 证据

- 红测 1：分镜连续两次改写原文，旧实现取消任务；修复后生成基础分镜，候选口播拼接等于冻结原文。
- 红测 2：分镜模型直接抛错，旧实现取消整稿；修复后只调用一次分镜模型并立即降级，已有口播照常形成候选。
- 红测 3：模型只吞掉段间换行，旧实现重试后仍可能失败；修复后一次调用完成原文重锚，且模型画面字段不丢。
- 防回归：首次分镜真实改字、第二次正确时继续采用第二次模型分镜，不误标为降级；旧账号覆盖继续走兼容单阶段。
