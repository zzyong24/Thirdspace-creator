# CreatorOS 模型调用延迟摸查（T-589）

> 类型：evidence（真实日志与代码事实）；日期：2026-07-28。<br>
> 范围：本机近 30 天加密 sidecar 日志、`runStructuredNode` 公共执行链、内容雷达“逐字稿 → 选题候选”。

## 一句话结论

内容雷达的“转换”并非本地字段转换，而是一次“完整逐字稿拆解 + 结合定位出题”的远端结构化模型调用。当前本机的生成型能力普遍需要约 59～69 秒，页面却只自动跟踪 8 秒；结构化输出失败时，默认重试与文本兜底还可能把尾部延迟继续放大。因此需要同时治理模型执行、拆解复用、可观测性和页面回显，单纯把转圈动画改快没有意义。

## 真实日志样本

从本机加密日志中共提取到 62 条带 `durationMs` 的记录。这里同时包含确定性工具、整轮对话和模型工具，不能把全体混成一个平均值；与模型生成直接相关的可确认样本如下：

| 能力 / 事件 | 真实耗时 | 结论 |
|---|---:|---|
| `topic.generate` | 68,893 ms | 选题生成本身已远超页面 8 秒跟踪窗 |
| `positioning.generate` | 61,313 ms | 不是内容雷达单点慢，生成型能力整体偏慢 |
| `topic.enrich` | 58,674 ms | 结构化选题补全同样约一分钟 |
| `material.gather` | 151,178 ms | 长上下文/工具型任务可超过 2.5 分钟 |
| `calibration.diagnose` | 15,032 ms | 较小输出的结构化任务明显更快 |
| `chat-turn`（25 条） | p50 23,450 ms；p90 106,025 ms；max 158,464 ms | 用户感知延迟跨度很大，必须显示真实进度而不是固定短轮询 |

附近日志明确记录 `script.draft`、`material.gather` 使用自定义 Anthropic 协议的 `MiniMax-M3`。`topic.generate` 的旧日志没有同时打印模型名，因此只能确认“同一时期的默认生成链大量使用该端点”，不能把内容雷达每次调用的具体模型冒充为已证实。

## 代码链路事实

1. 内容雷达把未经长度预算处理的完整逐字稿直接注入 `intelligence.topic-decompose`。
2. 一次调用要求同时产出 9 个字段：5 个来源拆解字段和 4 个新选题字段。
3. `runStructuredNode` 默认 `maxRetries=2`；结构化响应解析失败后，文本 JSON 兜底还会再尝试 3 次。
4. 单次模型调用硬超时为 90 秒。正常成功约一分钟；协议不兼容或输出不合格时，尾部延迟可能成倍增长。
5. 当前仓库有 41 个 `runStructuredNode({...})` 调用点，但公共执行层没有统一记录 template、耗时、token、重试和兜底路径。
6. 内容雷达页面仅执行 `20 × 400ms = 8s` 自动查询，随后停止跟踪并要求用户手动刷新。
7. 已完成的 `intelligence_transform.output_snapshot` 已包含拆解证据、`transcriptHash` 和 `decompositionVersion`，可以在 hash 一致时复用，无需新增数据表或改变数据归属。

## 根因排序

| 根因 | 影响 | 证据强度 |
|---|---|---|
| 当前生成模型/端点首包和完整响应慢 | 决定正常路径约一分钟的基础耗时 | 已由多条真实日志确认 |
| 页面只跟踪 8 秒 | 后台完成后页面仍像“卡住” | 已由代码确认 |
| 每次重新生成都重复发送完整逐字稿、重复拆解 | 增大输入 token 和重复计算 | 已由代码确认 |
| 结构化重试与文本兜底无统一打点 | 慢请求无法区分模型慢、重试还是协议降级 | 已由公共执行层确认 |
| 输出约束缺少上限和调用级输出预算 | 模型可能产生超出产品所需的长字段 | 已由 schema/调用参数确认 |
| 持久任务排队 | 本入口 enqueue 后立即 fire-and-forget claim，不是当前首要瓶颈 | 代码证据不支持其为主因 |

## 本任务采用的优化边界

- 首次生成继续读取完整逐字稿，不通过截断事实换速度。
- 同一逐字稿 hash 已有成功拆解时，重新生成只发送拆解证据与定位，模型仅生成新选题字段；最终结果继续合并原拆解证据。
- 内容雷达继续复用既有 `topic.generate` / 默认文本模型，不新增设置卡或专用 capability，避免继续堆高配置复杂度。
- 内容雷达调用收紧无效重试和输出预算，但不改变其它 AI 能力的可靠性策略。
- 公共结构化节点增加不含 prompt/响应正文的安全性能日志：template、耗时、路径、调用次数和 token。
- 页面以退避轮询持续跟踪真实终态，生成期间不锁死整个详情面板。

## 验收指标

1. 点击后 1 秒内显示任务已创建；超过 8 秒仍自动刷新，成功/失败无需用户手动点刷新才能出现。
2. 同一 `transcriptHash` 的重新生成不再把完整逐字稿传给模型，并有测试证明复用失效条件。
3. 首次生成的输出字段有明确长度/数量上限和输出 token 预算。
4. 日志可直接分辨主结构化路径、文本兜底、总耗时、模型调用次数及 token；不记录逐字稿、prompt、响应和密钥。
5. 内容雷达继续使用现有选题/默认文本模型配置，不要求用户理解或维护额外模型能力。

## 实施与验证

- 用户复核后否决额外的“内容雷达拆解模型”配置卡；最终实现统一复用既有
  `topic.generate` / 默认文本模型，不增加配置项。
- 同一逐字稿 hash 的第二次生成改走
  `intelligence.topic-from-decomposition`，输入不再包含整篇逐字稿。
- 内容雷达两条模型路径均设置 `maxRetries=0` 和明确输出预算；结构化协议落空时最多再发
  1 次文本兜底，不再额外放大。
- 最终聚焦回归：Backend 46 项、Frontend 104 项、AI Worker 全量 292 项通过，三包
  typecheck 和受影响前端 lint 通过。
- Backend 全量测试曾在两组全量 Vitest 并发运行时出现多个互不相关模块的 5～13 秒超时；
  停止重复进程后，受影响范围以单 worker 重跑稳定通过。该现象属于本机并发资源压力证据，
  不冒充产品逻辑回归或全量绿灯。
