# 标准版文稿与动效“迭代后无明显效果”诊断

> 任务：T-824
> 日期：2026-08-13
> 范围：只读核对安装包提交、正式运行日志、真实 DeepSeek Harness 稿件与成片；本报告不把旧样题评分冒充用户验收。

## 结论

用户体感成立，但文稿和动效不是同一个根因：

1. **动效改动没有进入当前标准版安装包。** 当前 `/Applications/CreatorOS.app` 及运行 sidecar
   仍为 `1.0.0`。T-793 的 SHIP Gate 锁定内容实现提交
   `1642c9980d96581840fa4bd091e68965d5233c12`（2026-08-12 10:43）；内容关系动效
   `c897fde2`（21:57）、可组合 Scene Graph `eb8ddc18`（2026-08-13 01:58）和主体放大
   `a4404d8c`（02:32）都晚于安装包冻结点，三个提交均不在该安装包祖先链中。当前成片只能走旧卡片，
   不是新动效“渲染了但看不出来”。
2. **文稿 Skill 确实运行了，但真实内容验收失败。** 2026-08-13 日志显示 `script.draft` 在当前
   DeepSeek 项目真实运行 5 次，输入约 1.2 万 tokens；T-793 又明确包含 `script.draft v9`。
   最近可核查的 v9 任务 receipt 显示该账号 `overlayVersion=null`，当前日志也没有出现 Skill 覆盖变更
   证据。因而现有证据不支持把问题归为“账号仍在调用旧 Skill”；问题是冻结样题的评分没有代表当前
   长分析稿的真实效果。
3. **真实成片暴露了时间真值断裂。** 稿面把整条脚本标为 `0–82s`，真实产出的 MP4 元数据为
   `130837ms`。模型填写的分镜时间没有约束住实际口播，后续视频只能依赖 SRT 重新对时；旧包又没有
   T-823 的“按当前 SRT 行绑定卡片”修复，于是出现字幕已讲可观测层、画面仍停在模式层。

## 文稿为什么“运行了 v9，仍像没变化”

### 1. 观点出现太晚

这条内容真正有认知价值的判断是“编排层、可观测层值得抄，模式层暂缓”。但成稿前 6 段、约前
64 秒都在依次解释 Cordis、组件、四种模式和事件流，直到第 7 段才开始权衡优劣。对观众而言，
前半段仍是仓库 README 导览，不是围绕一个新判断连续说服。

### 2. 上游结构与写作方法互相打架

`script.draft v9` 一方面要求“一个旧判断与一个新判断、每段继续推进”；另一方面又要求只要存在
结构方案、论点树或内容合同，就必须按它们的段落顺序铺分镜。当前项目恰好已经形成“四层架构逐层
讲解”的上游结构，弱模型优先完成了更具体、更容易校验的目录任务，认知对打退化成了提示词里的口号。

### 3. 第一次生成同时承担写作和制作

当前单次 `script.draft` 要同时产出口播、结构角色、画面、字幕、时长和素材引用。真实结果中第 7 段
单段达到 508 字，而 prompt 明明要求“一句话一个意思”；这证明提示词告诫没有形成可执行质量门。
模型把注意力分给制作字段后，最核心的“完整连续口播是否把人说服”没有独立产物，也没有独立验收点。

### 4. 昨日 Gate 证明的是样题，不是标准版真实旅程

T-790 的 `86 → 100` 来自冻结三题和专用评分器；T-794 的 Gate 还明确写着“不含用户真实模型端到端
出片”。这些证据能证明模板、契约和渲染器存在，不能证明当前 DeepSeek 长稿和安装版成片对用户可见。
今天的真实稿与真实成片应推翻“已验收”的主观质量结论。

## 根治方案

### 动效：作为 v1.1 发布候选的真实安装版验收

- v1.1 必须从包含 T-794、T-802、T-803、T-823 的同一冻结提交构建，禁止再用 T-793 的 1.0.0
  包证明新动效。
- 使用标准版真实模型重新生成 `video.cards`，任务 snapshot 必须记录 `video.cards` 的
  `baseVersion`，候选中必须真实存在 Scene Graph；不得手写 `visualPlan` 作为证据。
- 用用户当前 DeepSeek 主题和至少一个不同关系主题生成成片关键帧，验主视觉可读、内容关系不同、
  卡片随 SRT 当段切换；用户看不出区别即不进入发布冻结。

### 文稿：停止“提示词继续加长”，改为连续口播与制作分镜分责

推荐把现有一次模型调用改为两个可配置语义步骤，但保持用户仍点击一次“写稿”、候选/采纳/UI 公共契约
不变：

1. `script.voiceover.compose`：消费当前确认方向和完整受信资料，只产中心主张、观众旧判断、证据推进与
   一篇完整连续口播；先验“值不值得听、能不能一口气讲通”。
2. `script.storyboard.segment`：消费冻结后的连续口播和项目素材，切为镜头并补画面、字幕、时长、
   素材引用；服务端校验拼接口播与原文 hash 一致，禁止切分时偷改观点。

该方案会增加一次文本模型调用和相应等待时间，属于运行成本与内部 Skill 链变化。按项目流程，必须先写
SPEC、明确超时/失败恢复/账号覆盖兼容和真实盲选 Gate，经独立评审通过后才能 BUILD。
