## 最小合法处理方案

1. **先正式记录 T1426 的适用性裁决。**
   在 SPEC/DEC 中绑定上述源码提交与 CLI 用户要求，明确 UI journey 不适用、原 AC 与安全断言不减少；同步模块验证要求并独立复核。之后才可将验收元数据从“待验”纠正为非 UI 适用状态。状态仍由 `taskctl` 管理。无需修改中央 gate 实现、扩大忽略规则或伪造 frontend 报告。

2. **T1426 的完成仍取决于实际问题闭合。**
   UI 不适用不解决官方 Pi 的 402，也不等于所有组合通过；保持最终 CLI 回复、记忆、工具、准确错误分类及原任务恢复的证据要求。

3. **T1407 保留源 UI 与安装态义务，建立逐项证据对应。**
   复用 T1425 未变部分和来源已有成功记录，只补缺口、失败项和组合影响。若正式把 T1407 限定为“本地整合准备事实”的完成记录，必须同时把未闭合 UI 验收明确归属到现有后续修复任务，并继续作为推送前置条件；这不是把 UI 改判通过。

4. **继续完成不依赖 UI 工具的修复和验证。**
   可推进 CLI、HTTP→worker→durable、权限隔离、构建与静态检查。通过正常开发入口运行的真实浏览器可以补对应源码 UI 证据，但不能证明最终桌面安装态，也不能凭隔离数据证明月明水清深当前真实平台状态。

5. **工具限制不改变验收结果。**
   当前不能操控原生 UI 时，相关安装态验收保留待验。普通浏览器缺桌面握手而被拒绝属于正常安全边界；不注入凭据、不复制内部连接信息、不关闭鉴权。旧来源合同中的特定测试入口不能自动当成本轮绕过限制的依据。
