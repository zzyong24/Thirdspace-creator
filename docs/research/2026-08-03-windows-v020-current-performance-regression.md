# Windows v0.2.0 与当前包性能退化诊断

日期：2026-08-03  
任务：T-674  
结论类型：只读诊断，不改代码、不重新打包

## 一句话结论

当前 Windows 正式包没有沿用 7 月 26/27 日 v0.2.0 候选包已经验证过的“裁剪分层运行时”，而是退回了传统完整 runtime。结果是安装包从约 465 MB 增长到约 1.080 GB，安装时要同步校验并展开数量级更大的依赖树；在 Windows Defender 实时扫描下，海量小文件的落盘成本会被进一步放大。这是当前“安装慢、首启慢”的主因，不是用户电脑的错觉。

## 量化对比

| 指标 | 7 月 26/27 日 v0.2.0 候选包 | 当前 0.2.1-beta.3 | 变化 |
|---|---:|---:|---:|
| Setup 大小 | 465,187,198 B | 1,079,585,274 B | 2.32 倍，增加 614.4 MB |
| CI 干净安装 | 18.359 s | 约 1,207.8 s | 约 65.8 倍 |
| CI 干净首启到本地主页面 | 17.371 s | 约 28.115 s | 约 1.62 倍（慢 62%） |
| 运行时结构 | 裁剪分层 runtime，约 3,008 个文件、无 `node_modules` 目录 | 传统完整 runtime，包含完整依赖树并发生大量物化 | Windows 小文件 I/O 与杀毒扫描显著增加 |

证据来源：

- v0.2.0 对照流水线：GitHub Actions run `30300851671`，commit `ef0cd9a33efd45a8ccdf05bf529b528bdf0b8a81`。
- 当前流水线：GitHub Actions run `30786063714`，commit `ba15f09bbc1223118d2a17324d87d5018c0eb6d0`。
- 当前 Windows setup 精确大小由流水线 `ls` 输出；安装与首启耗时由步骤时间戳计算。

## 为什么会退化

### 1. 两版不是同一种 Windows runtime 结构

旧候选包使用 `tools/windows-closure-rat` 构建裁剪后的生产闭包：Next 运行时被收敛为 NCC/分层结构，最终安装 runtime 约 3,008 个文件，且验收明确要求没有 `node_modules` 目录。

当前正式 `build` job 则由 `frontend/scripts/desktop/build-sidecar.mjs` 组装传统完整 runtime。代码注释也明确写着：分层 runtime 仍在独立 RAT 验证，当前用户安装包继续使用“传统完整 runtime”。也就是说，曾经验证过的瘦身方案没有接进正式发布路径。

### 2. 当前包在安装阶段同步做大包校验和展开

当前 NSIS 只携带一个 `sidecar.tar.gz`，安装后通过 `ExecWait` 同步执行应用内置安装入口：

1. 对约 1 GB tarball 做 SHA-256 校验；
2. 把完整 runtime 展开到 `runtime-images`；
3. 校验入口与抽样完整性；
4. 写入 current 指针后才允许安装结束。

`ExecWait` 本身不是错误，它修复了以前“安装器提前返回、runtime 还没装完”的假成功。但当输入仍是完整 runtime 时，真实耗时就完整暴露出来了。

### 3. 传统 runtime 在 Windows 上发生大量目录物化与重复

当前构建日志显示：

- Windows Next 闭包扁平 hoist 61 包；
- Hyperframes hoist 201 包；
- Xenova Transformers 全树嵌套物化；
- 包外 symlink 又物化 80 项、约 150 MB；
- 仍有 Chromium、FFmpeg/ffprobe、本地 ASR/ONNX 等大二进制。

这些能力很多在旧分层包里也存在，因此“功能变多”不是 614 MB 增量的主要解释；核心差异是同一能力采用了更臃肿、重复度更高的传统依赖布局。

### 4. 为什么用户机器可能比 CI 更慢

GitHub Runner 的磁盘与 CPU 较稳定；普通 Windows 电脑还会叠加：

- Microsoft Defender/第三方杀毒对每个新落盘脚本、DLL、EXE 扫描；
- 机械盘或较慢 SSD 的小文件随机写；
- 8 GB 内存机器解压和杀毒并发导致换页；
- 首启时 Node 模块解析面对更深、更大的传统依赖树。

因此 CI 已经从 18 秒退化到约 20 分钟，用户侧出现更明显卡顿完全符合现有证据。

## 与“进入软件后页面卡”要分开看

本次证据可以确认：

- 安装包变大：已证实；
- 安装变慢：已证实；
- 干净首启变慢：已证实。

但“进入软件后每次切页面也慢”不能只由包体积直接推出。旧日志里的 cron 补跑风暴、本地 ASR 重试等问题已经有过单独修复；若当前用户仍反馈操作期持续卡顿，需要拿当前版本日志和进程 CPU/内存快照再单独判定，不能把旧版日志重复当成当前证据。

## 建议的修复方向

优先级最高的不是继续给传统包打补丁，而是把已经通过 RAT 的裁剪分层 runtime 正式接回发布 `build` job，并把以下预算变成正式发布硬门：

1. Setup 目标恢复到 500 MB 左右；
2. 安装 runtime 文件数不超过 3,500；
3. 正式 Windows 包不得含传统 `node_modules` 目录；
4. 干净安装不超过 5 分钟，目标恢复到 30 秒量级；
5. 干净首启保持在 20 秒左右；
6. 保留 Chromium、FFmpeg、ASR 等真实功能冒烟，不能用删能力换体积。

在这条主线完成前，只调 NSIS 压缩等级或隐藏安装进度都治标不治本。
