# T-915：浏览器实际关闭前保留启动占用

检查跨进程迁移边界时发现，原 chromium-guard 在启动超时后立即释放队列，但迟到 Chromium 可能仍活着；close 抛错也会在 finally 中释放占用。后继任务因而可能预检清锁或再次启动同一 profile。本批先修复这个实际生命周期缺口。

```mermaid
flowchart LR
 A[申请同一浏览器档案] --> B[有界排队]
 B --> C[启动浏览器]
 C --> D{超时或取消?}
 D -->|是| E[先返回状态、继续保留占用]
 D -->|否| F[正常使用]
 E --> G[迟到资源关闭成功或收到 close]
 F --> G
 G --> H[允许后继启动]
```

启动成功与迟到成功共用同一资源追踪。close 成功或真实 close 事件才释放；close 失败且无退出证据时保留占用。普通锁错误的一次恢复仍占据原队列位置，不与后继并发；真正启动失败则正常释放。取消可终止排队或启动等待，实际 launch 微任务再次检查取消，避免取消之后又新建浏览器。

排队默认使用同启动超时的等待上限，可独立配置；超时只撤销本次等待并提示档案仍被占用，不清锁、不释放前一资源。抖音 detail 默认启动闭包已向守卫传递原任务 signal，登录取流不再只能等 context 返回后才知道取消。

验证：新增生命周期 8 项、前端既有三文件 142 项，共 150 项不同测试通过；ai-worker 与 frontend 类型检查退出 0。覆盖启动超时迟到关闭、关闭失败、close 事件、排队取消、排队超时、锁失败恢复占用、同步异常、不同 profile 独立执行、启动微任务前取消。全部使用可控 context 和清理替身，不调用真实浏览器、进程清理或用户媒体。

原生命周期三项失败后修复；实现中一次锁恢复曾提前释放队列，也有当场红绿用例。独立复核指出 launch 微任务需再次检查 signal，当前已覆盖并复核。首次前端回归仅因超时文案缺连续“请重试”失败，已修正，未当作产品行为红测。提交环境缺少 lefthook，未宣称钩子通过。
