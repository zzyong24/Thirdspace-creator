# Windows 用户持续卡顿日志诊断（2026-08-02）

## 一句话结论

这次不是“用户电脑性能差”造成的普通卡顿。用户安装的 CreatorOS `0.2.0` 在后台自动化启动后，同时撞上了批量本地转写、无稿重建、封面回填与限流重试，Node 主进程出现了可观测的阻塞；最新一次启动又因一条旧版脏信源把整段抖音分享话术当 URL 解析，内容雷达页面重复报错。

## 证据来源

- 飞书记录：`rec27UEw1aIEqj`，提交时间 `2026-08-03 11:34:28`，系统为 Windows。
- 附件：`logs.rar`，包含 2026-07-28、2026-07-30、2026-08-03 的 6 份加密 sidecar 日志。
- 最新日志运行目录明确为 `D:\智能\CreatorOS\runtime-images\0.2.0-84b8b4ac7b68`。
- 日志不含操作系统级 CPU、内存采样，因此不把具体占用百分比写成事实；以下结论均来自任务数量、耗时与 Node 自身阻塞告警。

## 时间线复盘

1. 7 月 28 日的首次重任务运行，对最多 100 个缺封面作品做串行回填；抖音网关进入约 16 分钟冷却后，剩余候选持续快速失败。
2. 同一批导入作品又批量进入本地 Whisper 转写。Windows 运行时缺少 `@xenova/transformers`，产生 478 次失败；另一次运行产生 478 次 `fetch failed`。
3. 系统没有等到真实逐字稿，就为大量项目创建重建任务，最终 498 个 `reconstruct.project` 失败。
4. 上述后台工作与一分钟一次的自动化调度竞争同一 Node 进程，累计出现 185 次 missed execution。用户看到的“系统一直卡”与这一时间段完全一致。
5. 8 月 3 日最新运行中，自动化启动后约 5 分钟再次出现 missed execution。随后内容雷达在迁移旧信源时，把 `4- 长按复制此条消息…… https://v.douyin.com/...` 整段交给 `new URL()`，页面在 03:30 与 03:31 重复报错。

## 当前 main 的覆盖情况

### 已覆盖

- 本地 Whisper 打包：`frontend/scripts/desktop/build-sidecar.mjs` 已显式完整物化 `@xenova/transformers` 及传递依赖，Windows 使用无符号链接的真文件布局，并在出包前真实 `require()` 自检；旧包的“模块缺失”不会再静默带进安装包。
- 逐字稿与重建节流：`frontend/src/server/ingestion/reconstruct-enqueue.ts` 现在每轮默认只补 5 条逐字稿；只有项目已有真实逐字稿时才允许发起重建，不再为无稿项目制造 498 个注定失败的任务。
- 重活触发位置：封面/逐字稿重活已从轻量指标采集移到明细采集之后，并跳过绑号轻触发，避免每次轻量刷新都启动整批重活。

### 本轮已补齐（T-669）

- 存量脏 URL：旧信源迁移现在只在兼容路径从分享文案提取首个合法 `http(s)` URL，再执行统一 canonicalize；完全没有合法 URL 的旧记录进入 migration orphan 报告并跳过，工作区继续加载。新建信源仍使用严格 URL 校验。
- 封面回填止损：默认上限从 100 收敛到 10；共享抖音网关抛出 `DouyinCooldownActiveError` 时立即结束本轮，把当前及剩余候选诚实标记为 `deferred`，不再继续制造近百条失败和日志。

### 后续可观测性增强

- 缺少资源遥测：当前用户日志无法给出 CPU、内存、磁盘的准确曲线，只能由调度告警确认 Node 进程确实被阻塞。后续应补进程级采样，避免下一次只能靠间接证据定位。

## 建议处理顺序

1. 旧信源迁移兼容与封面回填小批量止损已在 T-669 完成。
2. 新 Windows 包继续保留 `@xenova/transformers` 硬自检；安装包验证时必须在干净 Windows 环境跑一次本地 ASR smoke test。
3. 后续增加 sidecar 进程 CPU、RSS、事件循环延迟与当前任务队列长度的低频日志，下一次可直接判断资源瓶颈。
