## 六、到"一个创作者能完整用起来的成品"还差什么

**功能完整度 89%,但"能端到端闭环运营"卡在飞轮两个物理接口:**

1. **必做(决定能不能用)**:
   - 采集通(数据进来)—— T-144 / T-136 §D;
   - 发布真平台(稿子发出去)—— 抖音发布适配器;
   - 搜索索引接线(全局搜索能用)。
   - 用户操作:配一个文本模型 key(解锁 17 个 AI)。
2. **增强(能用之后做强)**:多账号(多号运营)、桌面化(分发+加密+授权)。
3. **打磨**:L1 简化、论点编辑器、L5 录制、错误文案、注入加固、L7 复盘时序图。

**最短"跑通"路径**:修采集(输入)→ 配 key → 手动登记发布做复盘(输出可暂用登记补录)→ 飞轮闭环。真发布适配器和多账号、桌面化可随后。

## 七、对照产品定位精查的额外缺口(补漏,不阻塞单人跑通核心飞轮)

- **多账号 T-136 b~e 的真实缺口(比"待做"更深)**:backend `ctx.accountId` **零消费**,projects/artifacts/knowledge/positioning 等表**无 account_id 列**,`creator_profiles` 仍 `UNIQUE(user_id)` 单例。对"多号创作者"(核心用户画像)现在**根本没法按号隔离用**。含数据归属改动,是最大工程。
- **ChatBox 对话化覆盖不全(T-004)**:topic/script/brief/knowledge 已对话化+采纳门;但 **calibration/positioning/review 仍是表单、无对话化入口**;二/三波工具(planning 三件套/material.match/publish.platform_adapt)未接。
- **AI 自由文本节点残留**:多数已迁 `runStructuredNode`,但 `topic-enrich`/`review-runner`/`asset-classify`/`agent-run` 仍有自由文本/JSON.parse 路径(用户 MiniMax 下易 cancelled,应迁结构化)。
- **数据备份/迁移/导出几乎没有**:只有 1 个手动 sql dump,无备份/恢复/导出流程——单机产品用户数据是资产,这是缺口。
- **横竖屏 orientation 仅存字段无行为**:定位 §8 说唯一类型区分是横/竖屏,当前 brief 有字段但无差异化文案/结构行为。
- **发布层平台选择**(§8 平台在发布层选):`publish.platform_adapt` 工具未做。
- **可观测性**:除采集 throttleStatus 外,无统一错误上报/健康监控。
