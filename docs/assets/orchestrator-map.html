Why · 它解决什么问题

AI 写代码,
最贵的不是写错,是骗你

框架的基本假设:AI 会遗忘、会跑偏、会谎报"已完成"。所以状态、验证、恢复全部放在模型之外——这些事发生时,流程依然不被破坏。

INCIDENT / 01

假完成

"修好了""做完了"——但从没在真实环境跑过。单测绿 ≠ 真的能用。

实录:几十个任务全绿,集成走查发现 394 个缺陷、主流程 4 处断点。
INCIDENT / 02

假按钮

界面很漂亮,点开全是壳。UI 先画了,数据链路根本撑不住。

实录:详情页整排按钮 全部点不动——"先画后接"从此被禁止。
INCIDENT / 03

重造轮子

仓库里明明有现成实现,AI 不查就从零再写一遍,白烧几小时。

实录:一次会话内 3 次差点重造整个子系统,全靠开工前强制反证拦下。
INCIDENT / 04

上下文腐化

会话越长越糊,任务清单膨胀到塞不进上下文,新会话看不懂旧现场。

实录:任务看板膨胀到 204KB,单行 5933 字——注入即爆仓。
How · 五步交付管线

从一句想法,
到可发布的系统

五个阶段,只打扰你三次(①②③)。其余时间 agent 在门与证据链的约束下自己推进。

01 STAGE 1 / PLAN

规划一份章节化 SPEC

你说一句产品想法,agent 产出一份完整规格书:定位、用户、功能、流程、数据模型、信息架构。

  • 产品定位 = 项目宪法,之后每个决定都对照它
  • 跨模型审查:换一个"别家的 AI"来挑毛病,过审才继续
  • 自动判项目大小(S/M/L),小工具不搞大仪式
▌这一步拦住方向跑偏、需求散落在聊天里丢失、spec 里"仓库明明有却说没有"的空断言。
①
人类确认:这个产品是不是你想要的CONFIRM / PRODUCT_SPEC.md
02 STAGE 2 / CONTRACT

契约先证数据,再画界面

每一条功能,先回答:数据从哪来、存在哪、怎么读回来?逐条判定:可行 / 硬骨头 / 砍掉——不许留空。

  • 接口契约 = 前后端唯一真相源
  • 数据链路证明不了的功能,根本不允许进设计稿
  • 硬骨头(HARD)登记在案、指定归属,不许"以后再说"
▌这一步拦住"UI 画得出来、功能接不上线"——所有假按钮的总根源。
②
人类确认:范围信封,这就是要做的全部CONFIRM / SCOPE ENVELOPE
03 STAGE 3 / DESIGN

设计受契约约束的界面

现在才画界面。每个真实可点的控件,必须绑定到契约里已存在的操作——"No API, no UI"。

  • 绑不上的控件:要么改契约,要么明标「规划中」,要么不画
  • 每页四态齐全:加载中 / 空 / 出错 / 真数据
  • 探索性设计稿盖章「未经可行性核对」,不许直接开工
▌这一步拦住死 tab、假筛选、装样子的图表——界面不许承诺数据给不了的东西。
04 STAGE 4 / BUILD

实现垂直切片,数据第一天就是真的

一次做透一个能力:契约 → 后端(测试先行) → 前端接真 → 端到端回显,做完一片再拿下一片。

  • 每个任务先领"任务包":最小上下文 + 验收命令 + 改动边界
  • 并行 agent 各管各的文件区,唯一集成人串行合并
  • 假数据一出生就登记退役日期,健康项目的假数据账本接近空
▌这一步拦住"单测绿但没真跑过"、子代理死循环烧钱、并行互相踩脏文件。
05 STAGE 5 / SHIP

发布当一个真用户走一遍

不是看测试报告,是用真实数据把核心旅程亲手走通:每一步有命令、有输出、有截图,证据不齐不算完。

  • 集成走查:测试全绿也要人视角走主流程(缝隙里才有鬼)
  • 假数据账本清零、文档与代码零漂移,才准发
  • 发布评审留档:known risks 写明,别装完美
▌这一步拦住"每片都对、合起来是坏的"——切片验收 ≠ 产品验收。
③
人类确认:发布放行CONFIRM / RELEASE_REVIEW.md

SCENE 03 · 验收
