## 摘要(Executive Summary)

CreatorOS 是一套**编导式自媒体内容生产系统**(面向中文短视频/口播创作者),核心是「越用越准」的数据飞轮:创作 → 发布 → 采集真实表现 → 复盘校准 → 经验反哺下一条。技术形态为 Next.js 16 全栈单机应用(pnpm monorepo),数据本地存储、一机一创作者、不做多租户 SaaS。

**当前完成度出乎意料地高**:经全域盘点,产品的**创作侧(飞轮前半圈)完整可用**,AI 能力**全部实装无空壳**(配一个文本模型 key 即可用 9 个核心 AI 功能),辅助功能(设置/引导/首页/知识库/素材)基本可用。

**但存在一个决定性断点**:**抖音数据采集无法建立采集源(external_source),导致真实数据无法进入系统**——飞轮的"后半圈"(数据回流 → 复盘 → 经验)因此空转。这是全项目唯一的硬性功能断点,根因清晰、修复路径明确。

**一句话定性**:创作引擎已造好,只差"把真实数据这管油接进来"——修复采集是让产品从"半圈"变"整圈"的总闸。

## 1. 产品定位与目标

### 1.1 定位

**一个编导式的自媒体内容生产系统**——不是项目管理工具,而是一个越用越准的「编导智能体」:替创作者出选题、起草文案与结构、管素材;发布后采集真实表现回流校准,让下一条内容更准。

### 1.2 核心价值:飞轮复利(护城河)

```
盲预测 → 发布 → 采集真实表现 → 对照偏差 → 沉淀经验 → 回流让下一条更准
```

护城河是「越用越准」:用得越久,系统越懂这个创作者什么内容会爆。**数据是别人拿不走的资产**——存在用户本机,系统不上传。

### 1.3 生产流水线:两阶段

**脚本(稿面:选题/脚本/素材/发布动作一体)→ 复盘(数据对照/经验沉淀)。** 研究/策划/制作不再是独立阶段(职能由稿面承载);发布是稿面上的动作而非阶段。

### 1.4 核心原则(架构铁律)

1. 每个项目必须有 Brief;
2. 每阶段有明确交付物,前阶段产物自动流入下一阶段(SEAM 接缝);
3. **AI 只产候选,人确认关键产物**(AI 不直接写领域实体,走"AI 产候选 → 用户 UI 采纳 → backend 落库");
4. 复盘必须反向沉淀经验,回流选题/定位/校准;
5. 人出判断与品味,AI 出草稿、苦力、学习。

### 1.5 交付形态

**单机、本地优先**:一机一创作者,真实数据全部存在用户本机。当前为开发形态(手动起 dev server),规划演进为加密桌面双端软件(Windows/macOS,见 §5.4)。

## 2. 技术架构

### 2.1 Monorepo 结构

pnpm workspace,五个子包:

| 子包 | 职责 | 性质 |
|---|---|---|
| `frontend` | Next.js 16.2.9 + React 19,UI + API route + AI runner 装配 | 应用主体 |
| `backend` | 领域模块(projects/artifacts/knowledge/ingestion/…)的 service/repo | **纯库**(无 server 进程) |
| `ai-worker` | AI 节点(runStructuredNode)+ prompt 模板 + skill,Vercel AI SDK | **纯库** |
| `contract` | zod schema + operation 定义(180+ op) | 契约层 |
| `mcp-server` | stdio MCP 底座 | 可选集成 |

### 2.2 关键架构决策

- **进程内库调**:`POST /api/v1/dispatch` 收 `{id, input}` → `compositeTransport` → **直接 import backend/ai-worker 模块工厂,同进程构造 service/repo,无内部 HTTP**。前端 HttpTransport → Next route 只是 browser↔server-process 边界。
- **数据层三态**:`resolveDbDriver()` 支持 `DATABASE_URL`(Postgres)→ `PGLITE_DATA_DIR`(PGlite 落盘,零 docker)→ 默认 `~/.creatoros/db`。**桌面离线本地运行不缺数据库**(PGlite 是纯 WASM Postgres)。
- **单机免登录**(T-046):dispatch 无 session cookie 时回落"本机主用户直通";登录页保留但单机场景直通。
- **结构化 AI**:所有 AI 节点走 `runStructuredNode`(`generateObject + outputSchema`),**跨模型可解析**(不依赖某厂商的自由文本工具循环),用户可配任意 provider。
- **AI 确认门**:AI 只产候选(`recordCandidate`),经用户 UI 采纳才落领域实体;AI 不直接写库(架构铁律)。

### 2.3 数据资产隔离

所有业务数据存在数据库 + 本地文件,**代码仓库里一条业务数据都没有**。新用户拿到代码 = 空壳程序。数据分三处:数据库(作品/知识/定位/发布/配置)、`.auth/`(抖音登录态)、素材落盘目录。

## 4. 现存问题

### 4.1 P0 核心断点:采集源无法建立(编号 T-144)

**现象**:用户清空数据库后扫码登录抖音成功,但运行采集 → **新增 0 条**。

**根因(连库诊断坐实)**:

1. 扫码登录仅调用 `loginDouyin()` → 建立 `.auth/douyin` 浏览器登录态,**完全不创建 `external_source`(采集源)或 `platform_account`(账号记录)**;
2. **全仓根本没有创建 douyin `external_source` 的代码路径**(`createExternalSource` / `createSource` 零命中)——历史上 external_source 只靠启动时的 seed 注入,而 T-135(去 seed,让新用户开箱空)删除了该 seed;
3. 三个采集器(`self.metrics` 作品指标 / `comments` 评论 / `self.detail` 明细)在 `externalSourceId` 为空时,**fallback 到写死的常量 `"src-douyin-canonical"`**——正是被 T-135 退役的那个源;
4. `refreshDouyin` 的 `getExternalSource()` 查无此源 → 抛「外部来源不存在」→ 0 条。`self.detail` 还额外依赖已有 publications,空库形成死锁。

**影响面**:采集是数据飞轮的输入端。它一断,连带以下全部失效:真实作品导入、发布指标、评论、逐字稿、明细数据、复盘(无数据可对照)、经验(无复盘可沉淀)、依赖数据的 AI(复盘洞察/评论分析虽能跑但无有意义输入)。**这是"能创作、复不了盘"的根源。**

**修复路径**:补齐「扫码登录成功 → 落库建立真实 `external_source` + `platform_account` + 采集 job 绑定该源 + 采集器 fallback 不再指向 canonical(空源时报诚实错)」。此即多账号任务 T-136 的 §D 切片(见 §5.2)。

### 4.2 输出端断点:发布到真实平台是 Mock

**现象**:用户可"登记"已发布作品(补录元数据),但**系统无法替用户把稿子真正发布到抖音等平台**。

**根因**:`platform-publisher` 在 composition root(`persistence-client.ts:1086`)活体绑定的是 **`MockPublisher`**——内存记录 + 编造假 `externalId`(`mock:{platform}:{id}`),零网络请求。真实平台适配器(抖音/B站)仅有注释占位("stage-N swap")、未实现。

**影响**:飞轮的输出端未接真实世界。当前发布链路只能"事后补录",不能"系统代发"。对"编导创作 → 一键发布"的完整体验是缺口(但对"导入已发作品做复盘"的路径无影响,因那是补录)。

**修复路径**:实现抖音发布适配器(需平台自动化 + 账号授权),替换 MockPublisher。工作量中等,依赖平台发布能力调研。

### 4.3 基础设施:全局搜索索引未接线

**现象**:全局搜索(`/search`)对任意词基本返回空。

**根因**:搜索读侧(ILIKE 关键词 + `search_documents` 表)实装完整,但**没有任何模块在实体(项目/知识/素材/作品)增删时调用 `searchService.upsertDocument()` 写索引** → `search_documents` 永远为空 → 搜不到内容。`hybridSearch`(embedding 语义检索)代码完整但仅知识库私有搜索调用,全局搜索未接。

**影响**:全局搜索形同虚设(诚实返回空,非报错)。知识库内部搜索可用。

**修复路径**:在实体写入路径挂 `upsertDocument`(增量索引)+ 启动时全量重建;可选把 `hybridSearch` wire 到全局搜索。工作量小-中。

### 4.4 非 bug 类:需用户配置(设计使然)

以下不是缺陷,是"本地软件 + 用户自带 key"设计的必然:

- **AI 功能需配模型 key**:T-135 去除了预设 provider(避免泄漏开发者 key + 让开箱中性)。用户需在设置配自己的文本模型 key(如 MiniMax),解锁约 17 个文本类 AI;图/视频/ASR/embedding/搜索/视觉归类按需各配。全部诚实降级。
- **外观 theme/density 仅 localStorage**:未持久化到后端(轻微,单机可接受)。

### 4.5 技术债(已系统盘点,编号 T-145)

一位交互设计师提交了 60 条架构/文档/测试问题,经 7 组子代理逐条核实(真实约 31、部分约 18、明确误报 7)。已落地 5 类低风险修复(门卫假阳修复、控制工件去 stale、定位漂移收口等),其余分类为:

- **架构债(暂停)**:前端 3 个文件直连 Vercel AI SDK(应走后端)、3 个 service 文件 800–1200 行(可拆分)、`review/` 与 `reviews/` 目录命名歧义。已入门卫基线管理,重构择期。
- **测试覆盖**:review(审核,安全相关)、material-links、query-services 覆盖偏薄。
- **工程守门**:无 CI 跑门卫/reconcile;无 PreToolUse 硬拦。
- 详见 `docs/product-audit/2026-07-05-交互师60条核查台账.md`。

### 4.6 安全:AI 推理保护(待做)

- **prompt injection 面**:当前 `chat-runner` 将用户可控内容(复盘逐字稿/评论/选题标题)直接拼进 system prompt,**无 `<user_data>` 标记边界**——存在注入风险。这是待做的 AI 安全加固(见 §5.4 P4)。
- 抖音评论是最现实的注入入口。

## 5. 解决方案与路线

### 5.1 总原则

**先让核心飞轮端到端跑通,再谈加密/桌面化。** 阻断"闭环运营"的是三处未接真实世界的接口:①输入端采集(T-144,§4.1)②输出端发布 Mock(§4.2)③全局搜索索引未接线(§4.3)。其中**采集(输入端)是第一优先**——它一断,数据回流整条链空转;发布适配器与搜索索引可并行补。

### 5.2 P0:修复采集(T-136 §D)

多账号任务 T-136(一个用户可绑多个抖音号,每号独立人设)已完成切片 a(账号维度基座:RequestContext 加 accountId + 属主校验 + 账号切换器)。其 §D 切片正是采集修复:

- 扫码绑定 = 建 `platform_account` + `external_source` + 登录态(按 accountId 分目录);
- 采集 job 绑定真实源;采集器 fallback 去除 canonical、空源报诚实错;
- 采集结果按 account 归属(publications/指标/评论 stamp account_id)。

**一石三鸟**:消灭 T-144、打通数据回流、落地多账号核心。

### 5.3 内容功能:素材主权(T-146,进行中)

让用户上传的第一手资料(PDF/Word/MD)成为最高优先弹药——AI 写文案紧扣、搜索贴着它搜。切片 a+b(文档抽取链 + 优先级)已完成并验收,c+d(AI 硬约束注入 + 搜索结合)进行中。SPEC 已过 gate。

### 5.4 桌面化 + 资产保护(T-147,方向已定,原型已验)

演进为 Tauri v2 双端桌面软件。**P1 原型已验证可行**(`next standalone` build + PGlite WASM 端到端真跑通,推荐 sidecar 架构)。分 6 子项目:

- **P4 AI 推理保护**(ROI 最高、独立):`<user_data>` 包裹 + retriever rail + tool whitelist + sensitive class;
- **P5 授权**:复用已部署的自建激活码系统(activation-manager)+ Ed25519 签名加固;
- **P1 打包底座** / **P2 本地加密**(key→keychain)/ **P3 Prompt 远程管理** / **P6 客户端加固**。

**保护策略(经诚实评估)**:客户端代码无法真正防逆向(业界共识),故真护城河是**激活授权 + 持续迭代 + 数据飞轮在用户本机**,而非客户端加壳。详见 `docs/desktop-architecture-rfc.md`。
