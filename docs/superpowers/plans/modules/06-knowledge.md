# Module 06 — Knowledge — Executable TDD Plan (Wave 2)

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:test-driven-development` + `superpowers:executing-plans`. Steps are ordered TDD tasks; each `- [ ]` is bite-sized (one red→green cycle). This plan follows the **keystone** conventions in `docs/superpowers/plans/2026-06-21-program-foundation.md` §5 (per-module template) and §1 (architecture). Do **not** write implementation code outside the file paths named here.

**Goal:** Wire the **Knowledge** vertical end-to-end (FE button → contract op → user-scoped SQL → render) for the `/knowledge` page and the Research workspace (`/projects/:id/research`) notes/evidence editing. KnowledgeItem + KnowledgeRevision (append-only versioning) + KnowledgeRelation (knowledge graph). Real multi-tenant persistence on pglite; no AI in this module (AI authoring of knowledge is the AI module's `confirmResult`, out of scope here).

**Architecture (foundation §1):** New module under the Next app at `frontend/src/server/modules/knowledge/` (mirrors MODULE-ARCH §2). The proven Projects slice lives in `@creatoros/backend` (flat) and is the reference pattern; Knowledge is the first module to land in the **module registry** form: it exports `{ opId → handler }` and the composite transport unions it into `PERSISTED_OPS`. The `globalThis` pglite singleton in `frontend/src/server/persistence-client.ts` is shared by server reads and the `/api/v1/dispatch` route — Knowledge tables are added to the same db init. **Every repository query is user-scoped** (`eq(table.userId, ctx.userId)`); revisions/relations are scoped via their parent KnowledgeItem's ownership.

**Tech stack:** TypeScript · Drizzle ORM over `@electric-sql/pglite` (pure-WASM Postgres, no Docker) · `@creatoros/contract` Zod DTOs (the seam) · Next.js App Router (server components + client islands) · Vitest.

**Dependency note (must be GREEN first):** Wave 0 (registry generalization + Identity/auth giving `RequestContext.userId` + the `ctx` transport param) and Wave 2 **Projects** (the Research workspace lives under a project; `projects.get` and the project shell must resolve). Search + Taxonomy (Wave 1) provide tag chips but are **decorative** here, so they do not block Knowledge landing. Per roadmap §4 G6: deps = G5 (Projects) + G4 (Search/Taxonomy chips).

**Contract op ids this module owns (grepped from `contract/src/operations/knowledge.ts`):**
`knowledge.list` · `knowledge.create` · `knowledge.get` · `knowledge.revisions.create` · `knowledge.relations.create`.

## §12 state-machine note (this module)

SPEC §12 defines **no** transition diagram for Knowledge (confirmed: roadmap §4 line "No machine for Knowledge/Artifacts (append-only versioning)"). The two invariants the service enforces in lieu of a diagram:

1. **KnowledgeItem.status** is a 2-state lifecycle from the contract enum: `active → archived` (one-way; set `archivedAt` on archive). No archive op is in this module's contract surface (no `knowledge.archive`), so the service exposes the column + a guard but the **only** writes in this wave are create/revise/relate; items are born `active`. Do not invent an archive op.
2. **KnowledgeRevision is append-only / immutable** (SPEC §22 "ArtifactVersion immutable" applies by analogy to Knowledge versioning). `revisions.create` allocates the next `revisionNumber` (max(existing)+1, starting at 1) and **repoints** `KnowledgeItem.currentRevisionId` to the new revision; existing revision rows are never UPDATEd or DELETEd.

### B. repository (user-scoped — foundation §5.2)

- [ ] **B1 — Create `frontend/src/server/modules/knowledge/knowledge.repository.ts`** following `backend/src/repositories/project-repository.ts`. `createKnowledgeRepository(db, deps)` where `deps = { now: () => string; nextId: (prefix) => string }`. **`userId` comes from `RequestContext`, passed per-call, NOT baked into deps** (multi-tenant: one repo instance serves all users; the service threads `ctx.userId`). Signature note: every method takes `userId: string` as its first arg.
  - `seedKnowledge(rows)` — `insert(...).onConflictDoNothing()` (for canonical fixtures).
  - `list(userId)` — `select().from(knowledgeItems).where(eq(knowledgeItems.userId, userId)).orderBy(asc(knowledgeItems.createdAt))`. **User-scoped.**
  - `get(userId, knowledgeId)` — `where(and(eq(knowledgeItems.id, knowledgeId), eq(knowledgeItems.userId, userId)))`; throw `OwnershipError` (404, no existence leak — foundation §2) if no row.
  - `create(userId, { title, knowledgeType, content })` — UoW: insert the `knowledge_items` row (`status:'active'`, `sourceType:'manual'`, `sourceMetadata:{}`, `currentRevisionId` = the id minted next line), then insert revision #1 (`revisionNumber:1`, `content`) and `update` the item's `currentRevisionId` to that revision id. Stamp `userId`, `createdAt=updatedAt=now()`. Return the item row.
  - `createRevision(userId, knowledgeId, { content })` — `get(userId, knowledgeId)` (ownership gate), compute `nextNumber = max(revisionNumber)+1` via `select` over `knowledgeRevisions where knowledgeItemId = knowledgeId`, insert the new revision (append-only: never UPDATE existing), then `update` the item `currentRevisionId = newRevId, updatedAt = now()`. Return the **revision** row (matches `knowledgeRevisionResource`).
  - `createRelation(userId, sourceKnowledgeId, { targetKnowledgeId, relationType })` — `get(userId, sourceKnowledgeId)` **and** `get(userId, targetKnowledgeId)` (both ends must be owned — cross-user link → `OwnershipError`). Reject self-link (`source === target`) with `ConflictError`. Insert relation (`strength: "1"`, `createdByType: "user"`). Return the relation row, parsing `strength` to `Number`.
  - `getRevision`/`listRelations` helpers as the service needs (user-scoped via parent `get`).
  - **Integration test (`knowledge.repository.integration.test.ts`, pglite-backed): ownership enforced.** Seed user A's item + user B's item. Assert: `list(A)` returns only A's; `get(B, aItemId)` throws `OwnershipError`; `createRevision(B, aItemId, …)` throws (cannot revise A's item); `createRelation(A, aItemId, { targetKnowledgeId: bItemId })` throws (cannot link to B's item); `create(A, …)` produces revision #1 + sets `currentRevisionId`; a second `createRevision(A, …)` yields `revisionNumber:2` and repoints `currentRevisionId` while revision #1 row is unchanged (append-only).

## Open questions (flag at execution start; do not block planning)

The Research `证据收藏行` row maps to **`knowledge.relations.create`** (knowledge↔knowledge), not EvidenceLink. Confirm with the Artifacts plan that artifact-anchored evidence is theirs, so this module does not duplicate the `EvidenceLink` table.
2. **`knowledgeType` ↔ filter-chip labels.** Page chips are 全部/参考/笔记/片段/记录 (5) but the enum is `note/reference/inspiration/snippet/transcript` (5, with `inspiration` instead of a chip and `记录`≈`transcript`). Confirm the label→enum mapping (参考→reference, 笔记→note, 片段→snippet, 记录→transcript; 灵感/inspiration has no chip) — F1a maps display, no schema change.
3. **No `knowledge.archive` / `knowledge.relations.delete` ops.** Archive and unlink are referenced by the UI ("Add/edit/**delete** notes", evidence "unlink") but have no contract op in `knowledge.ts`. Plan treats them as **inert/disabled** (F2b). Confirm these stay out of Wave 2 scope rather than extending the contract.
4. **Research note ↔ KnowledgeItem resolution.** F2a assumes research notes are KnowledgeItems surfaced via the project's knowledge list. The exact read (project→knowledge join) belongs to the ProjectOverview/Research query service (Wave 4) or `ProjectKnowledge` (Assets/Projects). Confirm the read path that hands each note row its `knowledgeId`.
