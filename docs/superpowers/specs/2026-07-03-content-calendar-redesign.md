# 内容日历重设计:发布节奏的规划与达成回顾面

> SPEC 日期:2026-07-03 · 任务:T-083 · 状态:✅ PASS(2026-07-03 MiniMax 审,0 findings:真数据翻转务实、T-063R 样板拍板机制落地)——可开工(T-083a 样板先行)
> 用户裁决:「内容日历这里需要好好设计一下」。铁教训 T-063R:大改前端先做样板给用户真机预览拍板,再全量推进——本 SPEC 核心交付 = 设计方案 + 样板预览计划,不是直接全量实现。

## §0 第一性定位

日历对单人创作者只回答两问:**复盘(过去)**——发了什么、效果如何、断更空窗一眼可见;**排期(未来)**——哪天发什么、连到内容计划。对齐宪法两阶段模型:发布是稿面上的动作而非阶段,日历不是第三阶段,而是「发布节奏」的鸟瞰面——过去读发布真相,未来读排期意图,cadence 达成率把两者缝在一起。

## §0.5 现状盘点与真实密度(DB 实查 2026-07-03)

- **全链已有**:contract v0.4 八个 op(listCalendar/createEntry/updateEntry/transitionEntry/deleteEntry/getCadence/upsertCadence/getCadenceAttainment)、backend module(状态机 planned→published/missed + reconcile 读发布真相 + attainment 派生)、frontend feature `/calendar`(发布中心顶部链接卡跳入,T-052 并入)。
- **UI 现状 ≠ 日历**:三张 SectionCard 竖排(节奏编辑/新增计划表单/entry 平铺列表),无任何日历形态;窗口写死常量 `2026-06-22→07-20`(content-calendar-page.tsx)不随今天滚动。
- **数据真相(「做得很差」的根因)**:`content_calendar_entries` **0 行**——页面永远空,因为它只读手工 entries;而 `publications` 有 **73 条全部已发布** 的真数据它一条不渲。`scheduled_at` 全空;projects 无「计划发布日」字段;platform_accounts 1 个,cadence 1 行。
- **真实密度**:近月每周 1~3 条;峰值 2026-03(单周 13 条、单日最多 7 条);明显空窗(2025-10→12、2026-04 末~05 中、2026-06 上旬)。→ 设计贴「稀疏为常态、偶有爆发、空窗即信号」,不做假想满格视图。

## §1 设计

**核心翻转:过去格直接渲 publications 真数据(不靠手工 entry),未来格才用 entries。** 已发布项 → content_output → project 链路已通(SQL 验证),点开可跳稿面。

视图方案对比:

| 方案 | 一句话取舍 |
|---|---|
| A 月历格 | 空窗/节奏鸟瞰最强,但格子小、单日 7 条要折叠,详情看不了 |
| B 周列表 | 单条信息密度高,但空窗被跳过或占屏——恰恰丢了「断更一眼可见」 |
| **C 月历格 + 日详情抽屉(推荐)** | A 的鸟瞰 + 点格开抽屉看当天全部发布/计划,项目点开跳稿面;单日多条格内「+N」 |

C 细则:月格按 cadence 达成着色(达标/欠更/空窗三档,复用 attainment 派生);格内已发布项显标题缩略+播放数(播放全 0 归 T-082,照实渲不造假);月份可切换,窗口从注入的 referenceInstant 滚动派生(过 C-5 决定论,替换写死常量);未来格显 planned entry,可新增计划(复用 createEntry,可绑 candidate/contentOutput)。**「计划发布日」不加 projects 字段**——entry.plannedAt 已是排期真相,再加一处即双真相(YAGNI 砍掉)。
