# T-669 Windows 后台负载止损与旧数据兼容 SPEC

## 用户结果

Windows 用户升级后，即使本机保留了旧版写入的脏信源，也能正常进入内容雷达；后台补封面不会在抖音限流期间持续失败、刷日志或长时间占用网络与任务执行器。修复完成后从 `main` 产出 macOS 与 Windows 安装包。

## 已确认根因

1. 旧版 `trend_sources.url` 允许保存整段抖音分享文案，内容雷达首次迁移时直接 `new URL(...)`，导致 `getWorkspace` 抛出 `ERR_INVALID_URL`，页面请求反复失败。
2. 封面回填默认一次选择 100 条；共享抖音请求网关进入长冷却后，runner 仍逐条尝试后续候选，放大失败日志、任务耗时和系统负载。

## 实现约束

- 新建信源继续执行严格 URL 校验，不扩大产品输入契约。
- 仅在旧数据兼容迁移中，从分享文案提取首个有效 `http(s)` URL，并继续走统一 canonicalize。
- 旧记录完全没有有效 URL 时，迁移将其登记为 orphan 并跳过；工作区必须继续可用，不能因单条历史坏数据整体失败。
- 封面回填默认每轮最多 10 条。
- 普通的单作品下载或落库错误仍按既有语义继续下一条。
- 遇到 `DouyinCooldownActiveError` 时立即结束本轮；当前项及余下候选记为 `deferred`，不伪装成失败，也不继续调用抖音。
- `attempted = filled + skipped + failed + deferred`，日志只输出一次冷却止损摘要。
- 不新增第二套调度器、不绕过统一抖音请求网关、不让 runner 直接写数据库。

## 验收

1. 旧信源值为“分享文案 + 抖音 URL + 口令”时，迁移后 URL 被规范化且工作区可读。
2. 旧信源只有无效文本时，工作区仍可读，迁移账本记录 orphan。
3. 封面回填默认查询上限为 10。
4. 首条候选遇到长冷却时，后续候选不再发请求，结果为 `deferred` 而非批量 `failed`。
5. 非冷却错误仍能单条降级并继续。
6. 后端 intelligence 聚焦测试、封面回填聚焦测试、类型检查与架构边界检查通过。
7. 代码提交并推送 `main` 后，`desktop-release` 流水线的 macOS 与 Windows 构建成功，安装包作为 Actions artifact 留存。

## 发布与回滚

- 发布：手动触发 `desktop-release`，`only=all`。
- 回滚：代码回滚本次提交即可；迁移只新增合法新表投影和 orphan 账本，不修改旧表原值。
