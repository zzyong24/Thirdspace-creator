# T-819：普通对话自然语言定位并改写当前稿单段

> 日期：2026-08-13
> 状态：待独立评审
> 上游真相：[T-816 当前确认稿规格](2026-08-13-current-script-truth-and-natural-language-section-editing.md)

## 1. 用户结果

用户在项目普通对话中直接说“改第 7 段”“把项目对照那段缩短”或引用当前稿一句话，编导能读取当前确认稿、理解目标段并给出局部补丁候选，不再要求用户先点按钮或提供任何技术 ID。按钮入口继续作为更快的确定路径。

## 2. 交互流程

1. 普通项目对话同时提供只读 `context.artifact.text` 和候选工具 `script.patch`。
2. 模型必须先读取当前 `output_script` 快照，再按用户表达做语义定位；读取端同时签发只在当前工具回合
   可用的可信 `snapshotRef`，绑定 artifactId、currentVersionId、contentHash、sectionRef 集合与各段原文指纹；
   代码不做业务关键词正则、标题词表或字符串相似度匹配。
3. 模型从快照的 `sections[]` 中选择唯一 `sectionRef`，并提交该段完整 `replacementText` 与简短说明。
4. 服务端执行时从可信调用上下文取得 `snapshotRef`，不接受模型自报版本；按当前 RequestContext 重读当前
   版本，只有 artifact/version/hash、目标 sectionRef 与原段指纹仍与该 ref 一致时才返回既有
   `script.patch` 候选卡，任一变化都返回冲突并要求重新读取。
5. 用户采纳后复用 backend artifact service 的版本、段落与原文三重并发校验，只替换一段并追加完整新版本。
6. 模型认为零段或多段可能匹配时，向用户澄清内容语义；不得询问 artifactId、versionId、sectionId、hash 或让用户复制整稿。

## 3. 稳定段落引用

`sectionRef` 等于当前版本规范化段落的 `id`。已有唯一持久 ID 原样使用；历史版本缺 ID 或重复时，统一调用既有 `canonicalizeScriptSectionRecords`，按有可见内容的段落顺序确定性派生 `script-saved-N`，禁止随机 UUID。

同一个 `currentVersionId` 的稿面投影、`context.artifact.text` 读取和 `script.patch` 执行重读必须返回完全相同的顺序与 `sectionRef[]`。成功应用补丁生成新版本时，由既有 artifact 写入边界持久化规范 ID；不可变历史版本不回写。

## 4. 两种工具模式

- 按钮模式：已有受信段落锚点，工具参数仍只有 `replacementText` 和可选说明，维持局部改稿最小回合。
- 普通对话模式：没有按钮锚点但绑定当前项目时，工具参数增加 `sectionRef`；执行端把它当不可信选择，只用重读结果校验，不把模型自报值当授权。
- 两种模式的受信读取锚点都由运行时注入，按钮锚点或 `snapshotRef` 不进入模型可伪造参数；候选记录冻结
  创建时的版本、正文 hash 与原段指纹。
- 非项目对话不提供普通自然语言局部改稿；整稿生成/重写请求不被历史段落上下文强制成 `script.patch`。

## 5. no-op、换版与错误

- 工具封装发现规范化后的替换文本与当前原文相同，返回明确错误候选，不得宣称“已修改”。
- 前端候选卡禁用采纳相同文本；后端 `applyScriptPatch` 再次拒绝 no-op，不能新增版本。
- 候选产生后当前稿换版，采纳必须冲突关闭；用户重新发起时重新读当前稿。
- 模型完成读取但候选尚未创建的窗口发生换版时，工具执行也必须冲突关闭，不能把基于旧正文的
  replacementText 重绑到新版本中的同名 sectionRef。
- 零段、多段或引用已失效只结束本次局部动作，项目普通对话继续可用。

## 6. 物理边界

- AI 负责理解用户语义和改写，只产候选；代码只守归属、真实 ID、当前版本、唯一命中、并发、no-op 和用户确认。
- 浏览器与 frontend 组件只经 contract client / RPC；当前稿读取和补丁应用归 backend artifact service，AI runtime 只调用注入的公开端口，不直连数据库。
- 日志不记录稿件正文，只记录脱敏诊断引用、是否重读成功和匹配模式。
- 不做 T-814 统一聊天入口，不做 T-820 数据血缘，不自动采纳或覆盖稿面。

## 7. 验收

1. “改第 7 段”“把项目对照那段缩短”和引用原句三类表达都能由模型从结构化当前稿选择唯一段落，产同一种局部候选卡。
2. 用户全程不需要先点按钮或提供技术 ID；按钮入口仍通过既有回归。
3. 同一 `currentVersionId` 连续两次读取的 `sectionRef[]` 完全一致；历史无 ID 多段也可往返重读并在新版本自愈。
4. 零段/多段只澄清，整稿请求不触发单段工具，旧锚点不阻断普通对话。
5. no-op 在工具、前端与后端均失败关闭；换版后的旧候选不能覆盖当前稿。
   故障注入覆盖“模型已读 V1、候选创建前切到 V2”，证明不会生成可采纳的陈旧候选。
6. 采纳后刷新只改变目标段的用户可见正文，版本数增加 1；其余段落的标题、正文、类型、时间码、素材引用与顺序逐字段不变。历史无 ID/重复 ID 段允许写入规范化后的技术 `id` 作为唯一元数据变化，该变化不计为用户可见正文修改，并须单独断言除 `id` 外深度相等。
7. 相关 backend/frontend 单测、route 测试、类型检查、边界 Gate、reconcile 与真实项目浏览器旅程通过。
