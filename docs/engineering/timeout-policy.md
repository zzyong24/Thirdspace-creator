# 执行超时规范

单次业务执行、网络请求、结果等待、有限轮询总等待和构建探针的正超时最低两分钟。已有更长预算继续保留；转录、生成、渲染跟随原任务预算，不用两分钟取代十分钟或三十分钟。

```mermaid
flowchart LR
 A[原任务总预算与用户取消] --> B[内部步骤：每次执行至少两分钟]
 B --> C[串行步骤、排队、启动、重试和退避]
 C --> D[外层等待：覆盖全部内部预算并加结算余量]
 D --> E[返回真实结果或原任务ID继续观察]
```

- 数值原则：独立外层 > 所含内层完整墙钟预算。串行内层取总和，并计入所有尝试、退避、排队、冷启动和结算余量；并行内层取最慢路径。只把30秒改成120秒不能证明嵌套正确。
- 共享绝对deadline向内传播不是新小超时。原任务预算已耗尽立即停止，不能用下限重置。用户取消、归属/权限拒绝立即生效。
- 正超时由contract/timeout-policy归一；0/null禁用仅在原契约明确支持时使用，非法/溢出值拒绝。固定业务值及隐式库默认都必须显式审查。
- 心跳、轮询间隔、debounce、重试间隔、租约、TTL与输入媒体长度不属于执行超时。有限轮询的总等待属于；资源退出有限等待也需逐项记录，取消操作与回收宽限分开。
- 前端等候结束时保留原ID与后台真实状态。不能显示不存在的失败、自动重发或丢掉用户已选文件。
- 新增/修改超时必须列出消费者、完整调用链、超时效果、取消/资源回收和恢复入口。使用假时钟验证慢成功、子调用先超时、外层余量、串行重试、continuous、过期deadline与即时取消；至少一条完整公共调用链，不只孤立helper。真实供应商/安装版验证如未执行，明确待验。

本规范来源于已核实的固定30秒宿主等待误伤素材准备。详细逐条整改和防复发验证以T-1066交付为准。

落实时使用下表，不能把“最低两分钟”变成所有任务只给两分钟：

| 控制边界 | 当前策略 |
| --- | --- |
| 单次HTTP、页面动作/导航、执行探针 | 正值至少120秒；原180/300/600秒等更长值保留 |
| 浏览器两次启动 | 每次180秒，外层370秒覆盖两次尝试及10秒余量 |
| 新普通/自主持久任务 | 默认30分钟；新正预算首次冻结至少两分钟；历史期限不重算 |
| 转录、素材、采集 | 保留30分钟或原continuous策略；端口继承同一原期限剩余值 |
| 前端/CLI观察结束 | 原ID和真实运行态保留，可继续查询；不重新提交或取消后台 |
| 渲染依赖 | 同版本持久pnpm补丁，真实安装的页面默认/配置/CLI及关闭预算受门卫核验 |
| 停止与授权有效期 | 用户取消立即生效；取消后的500ms强杀宽限、TTL、心跳/重试间隔保持其本义 |

日常检查运行 `node tools/timeout-policy/verify.mjs`。全部原记录与保留原因见 `docs/verification/t1066/timeout-disposition.json`，完整证据和限制见同目录REPORT.md。依赖升级触发补丁哈希门失败时重新盘点SDK内部消费者，不能删门或只重拍一个helper绿测。
