## 实际结果

原 E2E `组内真实作业通过立即运行准入并保原任务显示待扫码` 在 390×844 视口失败，Playwright 实际退出码为 1，单次运行约 36.656 秒，未自动重试。失败发生在窄屏几何检查：主滚动区 `clientWidth=326`，`scrollWidth=530`，上限为 `327.5`。页面使用 64px 收起侧栏，剩余内容宽度与截图一致（390−64=326）。

我实际查看了 [原始失败截图](./original-common-failure.png)：账号组范围卡片内“筛选平台账号”的原生选择器明显越过窗口右边缘，确有可见的横向溢出；同一页的组名和账号标识也较长。错误上下文显示页面已真实加载账号组范围、平台/账号筛选、账号计划、快速创建和一条待扫码任务，因此这是产品页面的实际布局 RED，不是路由或空壳加载失败。该断言测的是整个主滚动视口，530px 超出 326px 也不能仅凭截图把溢出归因到某个单一控件。

原截图 SHA-256：`2c54c1f8e5b559bf1bc4404d734fc16eabcf14c5c24817d1ebde92c227702a18`。保全记录确认原测试 ID、标题、失败状态、错误及截图状态均未改，只把索引中的截图路径改指向这份字节相同的归档图；外部网络尝试为 0。

## 对选定 CSS 修复的判断

当前选定的 [filters-selected.patch](../filters-selected.patch) 仅含两个局部 CSS hunk：窄屏下账号组筛选区改成纵向布局、选择器受容器宽度约束；账号计划列表中的长账号名允许断行。它们直接对应截图里账号选择器出界和长标识撑宽容器的风险，范围与 3939 实际 RED 相符。当前页面文件 SHA 为 `21b0f1e361a569347349855dc71faece9fda6656ec90ee480627b05cc3cb8414`；该哈希是修复后的当前源，不是 3939 实际执行源。

这份旧 RED 证明修复前窄屏主滚动区存在横向溢出。patch 的结构看起来能约束所见的筛选控件和账号行，但尚不能由 3939 证明修复后全页 `scrollWidth` 回到范围内；仍需看 3940 的实际几何和截图。它也不覆盖快速创建卡片、任务详情/扫码面板等其余窄屏断言。故当前结论为“原布局缺陷已由真实 RED 证明；选定的两段修复与缺陷点匹配；修复是否消除溢出待 3940 实测”。
