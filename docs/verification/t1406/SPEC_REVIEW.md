### I-02：新组私有与历史共享兼容

现有 `backend/src/modules/review/review-gate.repository.ts` 的单条读取、列表与 active 读取均仅按 `userId` 约束。只在列表增加组过滤会使实际审稿继续使用另一组规则；直接把全部 NULL 旧记录过滤掉又会让既有 active 规则静默失效。SPEC 已同时禁止这两条错误路径，兼容决策合理。

实施必须保留以下约束：

1. 新建私有规则的归属来自真实服务端工作区上下文；不能信任浏览器任意 `groupId`，不能把后台回流规则写成新的无组共享记录。缺少真实组身份时按原入口语义明确拒绝或保留显式兼容路径，不能猜当前组。
2. NULL 旧记录原样保留，只在同一用户的显式历史共享层可见；不能自动归组、复制到每组或修改旧记录状态。系统种子与历史自定义规则应有可辨识说明，不能把全部旧自定义规则冒称系统规则。
3. 列表、单条读取、修改、删除、执行 active 规则必须共用一致的私有/共享可见性边界，继续保持跨用户拒绝。历史共享规则修改的影响范围应在 UI 明示。
4. 必须用隔离旧库升级测试保留旧 active 行与有效性，并覆盖同用户组 A/B、另一用户、新私有规则、旧 NULL 自定义规则和系统种子；不能只测试新空库。

### I-06：真实来源、事务与幂等

SPEC 要求服务端采纳回执、真实来源身份、原子勾选与可编辑内容、同一事务提交和刷新恢复，足以约束重复入库的根因修复。实施时不能以正文相同或前端禁用按钮替代真实来源与回执。

1. 稳定候选身份应绑定真实聊天工具/任务结果及原候选位置或标识，不能仅用用户编辑后的正文哈希作唯一键；同一原子编辑后重试仍必须命中同一已采纳回执。
2. 服务端需校验用户、组、任务/消息/工具结果的真实归属与候选存在性，不接受客户端虚构来源 ID 或用标题猜测来源。旧无来源卡应诚实说明不可恢复或走明确的旧兼容入口，不伪造成功来源。
3. 原子、可选原文归档、知识修订及采纳回执必须在同一真实事务边界内提交。事务失败不能留下半份笔记；并发保护必须有数据库唯一性或等价原子锁定，不能只有进程内集合。
4. 覆盖顺序重试、并发、提交后响应丢失再回读、不同编辑正文重试、跨组/用户拒绝、勾选子集与原文归档选项；普通手工 `knowledge.create` 保持原行为。已采纳内容后续编辑应走显式修订，不能以新的采纳重试制造副本。
