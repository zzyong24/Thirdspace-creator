# T1191 当前界面独立视觉评审

本轮是 oil-ui-pro 0.10.0 的“给已有界面评审”，只看当前截图与现有规范，不评分。目标是保留 CreatorOS 既有紫色、丰富工作台方向，让用户看清稿件未准备好、引擎未就绪和提交结果未知时的下一步。没有建议更换品牌色、Noto Sans SC、组件库或整体布局。

已实际查看 18 张当前截图：4 张 100% 准备/引擎状态、2 张 100% 提交未知状态、4 张全局宿主 200% 初态、4 张交接所称标准滚轮后状态、4 张交接所称控件聚焦后状态。200% 的 1280×800、900×600 物理图分别对应 640×400、450×300 逻辑视口。每张图的完整路径、SHA-256、尺寸与范围见 [READ_SET.json](READ_SET.json)。材料无缺失。

## 第一部分：偏离现有规范的地方

### D1：关键状态说明被排成辅助小字

- **位置**：100% 准备、引擎未就绪和提交未知状态卡中的说明正文，以及“继续本轮”“核对原请求”等恢复操作文字。
- **观察**：状态卡标题比正文醒目，但“本轮尚未发送”“原请求结果待确认”下面承担结果解释的文字，在 100% 图中呈现约 12px 的阅读尺度。200% 全局图中的对应正文约为 24 物理像素尺度，即约 12 逻辑像素。这是画面估算，不是 CSS 测量结论。
- **规范依据**：`UI_RULES.md` 要求产品正文 14–16px；oil-ui-pro 的可读性与操作文字参考也从 14–16px 起步。这里的信息决定用户是否继续或核对，不能只按脚注来排。
- **调整方向**：在现有字号变量及 Button 变体中提升关键正文、恢复操作的阅读尺度；辅助拖放说明和快捷键仍可退后。不要通过扩大整个界面或重新设计卡片解决。
- **验证**：实现方核对实际字号，并用相同内容在 100% 和 200% 阅读尺寸复看。字号提升后仍应完整换行，不能靠固定高度裁切。

没有从当前画面观察到另起品牌方向、新增发光、玻璃或装饰渐变等明确偏离。精确色值、字体是否实际加载、数字字形、组件归属与圆角 token 无法单凭截图确认。本次没有读取源码，不能把这些项写成已通过。100% 材料是局部组件隔离画面，不能据此评价完整首页是否保留全部工作台卡片。

## 第二部分：最有依据的三处完成度问题

### 1. 提交未知时，同一原话仍呈现为可以再次发送的输入

- **位置**：`final-source-walk-prepare-1280x800-submitted-unknown.png` 的结果待确认卡与底部输入区。
- **观察**：右上对话气泡已显示“这次明确修改”；状态卡写“原请求结果待确认”“正在等待原会话回执”，核对入口呈灰色低对比外观。底部输入区仍保留同一句“这次明确修改”，旁边发送箭头保持实心紫色外观。creation 的提交未知图则显示原请求气泡，输入区已回到空提示，两条路径的可见表达不同。
- **影响**：用户会犹豫这句原话究竟是已进入等待的请求，还是需要再次发送的草稿。状态卡本身没有伪装成功，但下方控件外观削弱了“先等原回执”的判断。这是**可见状态歧义**，不是已证实的自动重发、重复提交或按钮实际可用结论。
- **建议**：统一两条路径的呈现。待确认原请求继续留在既有对话气泡与状态卡中，底部不要继续把同一句原话显示成待发送草稿；需要保留其他新草稿时应明确其身份。继续复用现有输入区、状态卡和按钮，不增设新的提交流程。核对入口可在不可核对的外观下直接写出“等待回执”，可核对时再恢复“核对原请求”。
- **验证**：以同一原话分别进入 prepare 和 creation 的提交未知状态，检查用户能否从画面准确指出原请求、当前等待状态及下一步。真实按键、点击、请求幂等与回执仍需另外验证，本轮没有执行。
- **性质**：应修复的任务状态表达问题；本轮不把它判成已发生的行为阻断。

大白话：原请求正在等结果时，同一句话不要同时看起来还等着再发。

### 2. 最重要的结果解释比输入草稿更难读

- **位置**：全部 100% 状态卡，尤其 prepare 的“本轮尚未发送……”与提交未知的“原请求未重复提交……”说明。
- **观察**：状态标题可识别，正文与恢复按钮却比底部草稿/空提示明显更小。用户要依靠这段小字理解“没有发送”“已保留”“等待原回执”，而不是只读标题即可作决定。对应 D1。
- **影响**：视觉阅读顺序优先照顾了输入区，承担安全恢复判断的正文退成辅助信息。放大后文字本身清楚，但 100% 日常阅读仍需要额外辨读。
- **建议**：用现有 14px 正文与操作字号档承载状态原因和恢复动作，保留现在的标题、语义颜色和卡片样式；先删重复介绍文字回收空间，再调整自然高度。状态原因、原请求身份和下一步不能作为减法对象。
- **验证**：相同数据的 1280×800、900×600 100% 截图应能直接读清原因与动作；200% 复看换行与卡片自然高度。此项是阅读尺度问题，不是换字体或换风格建议。
- **性质**：规范与可读性修正；截图不证明用户已实际读错。

### 3. 短高全局弹窗把故障原因与恢复动作分成了几段阅读

- **位置**：200% 全局宿主，尤其 450×300 逻辑视口的 prepare/creation 初态、滚轮后与聚焦后截图。
- **观察**：初态中外层“AI 助手”、内层“编导对话＋描述”、新对话/历史和项目条占用较多垂直空间，状态卡主要露出标题，原因和恢复动作在下方。滚轮后能看到“继续本轮”或“检查编导引擎”，但原来的状态标题与部分原因已移出可见区。发送控件聚焦后也能进入可见区。640×400 的引擎状态原因和恢复动作能一起看见；prepare 的动作需要继续滚动。
- **影响**：恢复路径需要读者在几个滚动位置之间记住原因和当前对象。它增加阅读负担，但**这些提供的状态已显示控件可以进入可见区**，不能据初态首屏裁切认定任务不可达，也不能把静态过程图当成实际操作通过。
- **建议**：保留既有 Dialog 与工作区结构，在短高全局承载中优先删除内层重复介绍、收紧标题区的垂直留白，让状态原因与恢复动作尽量同屏。外层标题、关闭入口、项目身份、新对话和历史继续保留。使用既有间距变量与组件，不新增弹窗体系，不通过缩小正文塞进首屏。
- **验证**：在 640×400 与 450×300 逻辑视口复看初态和正常滚动状态：原因与恢复动作能连续阅读，滚动时对象身份可重新找到，聚焦入口完整可见。长内容允许滚动，不要求所有内容首屏装完。真实滚动、键盘顺序和操作结果仍是未验项。
- **性质**：空间与阅读连续性的改进建议；当前材料不支持任务阻断结论。

## 可以直接删掉的文字

- 全局“AI 助手”承载内的“描述你的目标，我来帮你规划下一步”可删。这句是重复介绍，没有帮助当前故障恢复。独立组件的标题是否删去不在本次建议内。
- 没有建议直接删除“尚未发送”“已保留”“等待原会话回执”等状态信息；它们承担当前任务必需的区别。

本轮只评审，没有实际删文案或调整细节。

## 看得出的细节

- 450×300 的 creation 聚焦图中，“编导引擎”的“引擎”被分到两行；滚轮后输入提示的“选题”也被拆开。可对这些短词使用既有不拆行方式，或缩短提示句，不锁住整段长文本。
- 引擎设置入口的紫色焦点外观清楚，与品牌色呼应。prepare 的发送聚焦截图没有同样明显的外圈；仅凭图片不能判定真实焦点样式或键盘行为是否缺失。
- 当前可见区域未观察到正文重叠、主按钮文字碰撞或同类按钮明显错位。不以图片推断真实 disabled、处理中或可访问名称。
